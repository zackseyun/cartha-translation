## Exact local workflow

The new executor is `tools/genesis_note_transaction.py`. It has **no canonical writer**. Commands use non-optimized Python; prior frozen checks contain assertions.

1. Run `.venv/bin/python tools/genesis_note_transaction.py` for read-only implementation preflight at the exact baseline. Independent review must bind every `binding()` field, including executor, new tests, this document, exact test-migration plan, dependency manifest, candidate, judgment and frozen preflight, and explicitly set `scoped_transaction_approved: true` in `genesis4_8_newtransaction_review.v1.json`.
2. Only after that review, run with `--prepare-intent`. This creates `genesis4_8_newtransaction_intent.v1.json` exclusively, requires baseline and no existing ledger, and binds the exact review bytes and complete preflight. It changes no YAML.
3. The parent applies the exact approved candidate separately with `apply_patch`. The connected current-test migration is separately specified by exact before/after hashes and five replacements in `genesis4_8_newtransaction_test_migration.v1.json`; it has not been applied by this implementation. Its context loop explicitly passes the active `Path.read_bytes` reader, rather than the Numbers helper's import-time default, so outer historical views are honored. None of the existing 101 context paths is the Genesis or Jeremiah target, but the intended composition is kept explicit.
4. Run with `--confirm-application` only after that edit. Exact candidate bytes, current review/intent bindings, frozen historical replay, actual current full GEN export and complete corpus checks must pass. The exclusive receipt path is `genesis_4_8_note_application.v1.json`, as already declared inside the frozen candidate.
5. Run `--post-check` for independent read-only verification of the completed state. Missing application, missing intent, wrong ledger status, stale exact review/executor/intent bytes, unknown target bytes and unrecorded rollback all fail closed. The exact review, intent and application bytes are rechecked after validation. A retry cannot overwrite either ledger; interrupted or reversed transactions need explicit investigation, not automatic ledger replacement.

Ledger creation reuses the already pinned exclusive-create/fsync helper. Checks revalidate package/review bindings around work and detect corpus/target changes. This is a local controlled workflow, not an atomic multi-file transaction or protection against arbitrary concurrent external writers; the parent must avoid concurrent edits while applying and confirming. No deployment command is authorized.
